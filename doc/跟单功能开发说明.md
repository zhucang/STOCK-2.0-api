# 跟单功能开发说明

## 1. 功能目标

本次新增需求为“复刻币安的跟单功能”，当前后端已先按“加密货币合约跟单”场景完成第一版基础能力建设。

本版目标主要包括：

- 支持配置可被跟随的交易员
- 支持普通用户跟随交易员
- 支持交易员开仓后，系统自动为跟随者同步开仓
- 支持交易员平仓后，系统自动为跟随者同步平仓
- 支持后台管理交易员和查看跟单关系
- 支持通过 Flyway 自动执行数据库变更

当前实现重点在后端能力和数据库结构，前端页面、后台菜单权限、运营配置项可在后续继续补充。

## 2. 当前实现范围

当前版本已经实现的范围如下：

- 跟单交易员实体、Mapper、Service、Controller
- 跟单关系实体、Mapper、Service、Controller
- 主单与跟单单映射实体、Mapper
- 用户端跟单 API
- 后台交易员管理 API
- 后台跟单关系查看/删除 API
- 在 `UserCryptocurrencyPositionServiceImpl` 中接入开仓/平仓同步逻辑
- 使用 Flyway 新增数据库迁移脚本

当前版本未覆盖的范围如下：

- 股票跟单
- 外汇跟单
- 期货跟单
- 后台菜单、按钮权限、前端页面
- 用户端收益排行榜、交易员业绩统计页
- 跟单风控参数的后台可视化配置

## 3. 核心业务设计

### 3.1 角色说明

- 交易员：可以被其他用户跟随的人
- 跟随者：创建跟单关系并自动复制交易员开平仓的人
- 主单：交易员本人开出的仓位
- 跟单单：系统为跟随者自动创建的仓位

### 3.2 跟单模式

当前支持两种模式：

- 固定金额模式：每次跟单都按指定保证金金额开仓
- 按比例模式：跟单金额 = 交易员主单保证金 * 跟单比例

### 3.3 主从订单关系

系统不会直接修改原有持仓表结构来记录父子关系，而是新增独立映射表保存主单和跟单单之间的绑定关系。

这样做的优点是：

- 对现有交易系统侵入更小
- 后续更容易扩展到期货、外汇、股票
- 更容易做数据回溯和问题排查
- 不会破坏原有持仓模块的使用逻辑

## 4. 数据库设计

本次数据库变更通过 Flyway 落地，脚本位置如下：

- `ruoyi-admin/src/main/resources/db/migration/V196__copy_trade.sql`

### 4.1 copy_trade_trader

交易员配置表。

主要字段：

- `user_id`：交易员对应的用户 ID
- `trader_title`：交易员展示标题
- `trader_desc`：交易员简介
- `status`：状态，`0` 启用，`1` 停用
- `min_follow_amount`：最小跟单金额
- `max_follow_amount`：最大跟单金额
- `max_follower_count`：最大跟随人数
- `default_follow_mode`：默认跟单模式
- `default_follow_ratio`：默认跟单比例
- `sort`：排序值

### 4.2 copy_trade_relation

跟单关系表。

主要字段：

- `trader_id`：交易员配置主键
- `trader_user_id`：交易员用户 ID
- `follower_user_id`：跟随者用户 ID
- `follow_mode`：跟单模式，`0` 固定金额，`1` 按比例
- `follow_amount`：固定金额模式下的金额
- `follow_ratio`：比例模式下的比例
- `max_open_orders`：最大同时持仓数
- `status`：状态，`0` 跟单中，`1` 已停止
- `last_follow_time`：最近跟单时间

### 4.3 copy_trade_order

跟单订单映射表。

主要字段：

- `relation_id`：跟单关系 ID
- `trader_user_id`：交易员用户 ID
- `leader_position_id`：主单持仓 ID
- `follower_user_id`：跟随者用户 ID
- `follower_position_id`：跟单单持仓 ID
- `status`：状态，`0` 持仓中，`1` 已结束
- `remark`：备注信息

## 6. 关键流程说明

### 6.1 用户创建跟单关系

流程如下：

1. 用户调用 `/api/copyTrade/relation/follow`
2. 后端校验交易员是否存在且启用
3. 后端校验用户不能跟随自己
4. 后端校验是否已有启用中的跟单关系
5. 后端校验交易员跟单人数上限
6. 后端校验跟单模式和金额/比例是否合法
7. 如果是历史停用关系，则恢复该关系
8. 如果是首次跟随，则新建关系

### 6.2 交易员开仓后同步跟单

流程如下：

1. 交易员调用原有加密货币合约开仓逻辑
2. 主单创建成功后，调用 `copyTradeService.handleLeaderOpenPosition(position)`
3. 系统判断当前用户是否为启用状态的交易员
4. 系统查询该交易员的所有启用中的跟单关系
5. 对每个跟单关系校验最大同时持仓数
6. 为符合条件的跟随者调用 `openCopyTradePosition(...)`
7. 创建跟单持仓后写入 `copy_trade_order` 映射表

### 6.3 交易员平仓后同步跟单

流程如下：

1. 交易员调用原有平仓逻辑
2. 主单平仓成功后，调用 `copyTradeService.handleLeaderClosePosition(position)`
3. 系统查询该主单对应的所有未结束跟单映射
4. 逐条调用原有 `sell(...)` 方法强制平仓跟单单
5. 平仓成功后，将映射状态更新为已结束

## 7. 事务设计

本次实现中，跟单同步采用了“主交易成功优先”的设计原则。

### 7.1 交易员本人下单优先成功

交易员本人开仓和平仓，是核心交易动作，必须优先保证成功。

因此设计为：

- 主单交易逻辑成功后，再触发跟单同步
- 如果某个跟单人同步失败，只记录异常日志
- 不回滚交易员本人已经成功的开仓或平仓

### 7.2 跟单同步使用独立事务

`CopyTradeServiceImpl` 中：

- `syncFollowerOpenPosition(...)`
- `syncFollowerClosePosition(...)`

都使用了 `REQUIRES_NEW` 独立事务。

这样做的目的是：

- 单个跟单人失败不影响其他跟单人
- 单个跟单人失败不影响交易员主单
- 便于后续对失败数据做重试或人工排查

## 8. 异常处理设计

所有跟单同步过程中的异常，都会记录到：

- `scheduled_task_exception_log`

记录方式包括：

- 异常任务名
- 异常简要信息
- 异常堆栈
- 关联主单或关系 ID

这样做的目的，是为了不打断主交易流程，同时保留完整排查依据。

## 9. 用户端接口说明

### 9.1 查询交易员列表

接口：

- `GET /api/copyTrade/trader/list`

说明：

- 只返回启用状态的交易员
- 默认按 `sort` 和 `id desc` 排序

### 9.2 查询交易员详情

接口：

- `GET /api/copyTrade/trader/{id}`

### 9.3 查询我的跟单关系列表

接口：

- `GET /api/copyTrade/relation/myList`

说明：

- 后端强制只查询当前登录用户自己的关系

### 9.4 创建跟单关系

接口：

- `POST /api/copyTrade/relation/follow`

请求体示例：

```json
{
  "traderId": 1,
  "followMode": 0,
  "followAmount": 100,
  "maxOpenOrders": 5
}
```

或：

```json
{
  "traderId": 1,
  "followMode": 1,
  "followRatio": 0.5,
  "maxOpenOrders": 5
}
```

### 9.5 停止跟单

接口：

- `POST /api/copyTrade/relation/unfollow`

参数：

- `relationId`
