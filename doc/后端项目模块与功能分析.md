# 后端项目模块与功能分析

## 1. 文档说明

本文档基于当前仓库代码结构整理，分析范围仅覆盖后端，不包含 `ruoyi-ui` 前端。

分析目标：

- 说明项目后端的模块划分
- 说明各模块承担的职责
- 归纳当前系统已经实现的主要业务功能
- 帮助后续开发、排障、接手和二次改造快速建立整体认知

当前分析时间基线：

- 代码仓库当前分支：`master`
- 工作区状态：干净


## 2. 项目总体判断

该项目不是“标准若依后台”这么简单，而是一个基于 RuoYi 深度定制的金融交易类后端系统，已经覆盖了：

- 用户与账户体系
- 资金充值、提现、划转、彩金、账变
- 多类交易产品
- 合约/现货/理财/质押/贷款等业务
- 多语言与站点内容管理
- 支付通道与第三方接入
- 定时任务驱动的撮合、强平、止盈止损、派息、新闻抓取等自动流程

从代码规模上看，当前后端已具备明显的“业务平台”特征，而不是单体管理后台的轻度改造。


## 3. 技术栈与运行特征

### 3.1 基础技术栈

- Java：`1.8`
- Spring Boot：`2.5.15`
- 权限与认证：Spring Security + JWT + Redis
- 持久层：MyBatis XML
- 分页：PageHelper
- 数据源：Druid + MySQL
- 缓存：Redis
- 数据库迁移：Flyway
- 定时任务：Spring `@Scheduled` + Quartz

### 3.2 运行配置特征

主配置文件：

- `ruoyi-admin/src/main/resources/application.yml`
- `ruoyi-admin/src/main/resources/application-druid.yml`

当前默认运行参数：

- 服务端口：`9201`
- 数据库：`stock`
- Redis：`localhost:6379`
- Spring Profile：`druid`
- Token 过期时间：`1440` 分钟

### 3.3 时间与调度特征

主启动类中显式设置了系统默认时区：

- `America/Toronto`

这会直接影响：

- 定时任务执行时点
- 订单过期、派息、日报、结算逻辑
- 业务时间判断与数据库时间解释


## 4. 模块结构总览

后端 Maven 模块如下：

| 模块 | 作用 |
| --- | --- |
| `ruoyi-admin` | 应用启动入口、控制器暴露、配置文件、Flyway migration |

- `system` 目录承担后台运营、配置、审核、报表、基础数据维护等职责
- `api` 目录承担 APP/前台业务接口职责
- `lianghua` 目录是量化机器人接口的定制扩展

### 5.2 `ruoyi-framework`

职责：

- 安全配置
- JWT 登录态解析
- 跨域处理
- 全局异常处理
- 数据权限切面
- 重复提交拦截

关键能力：

- `SecurityConfig`：统一安全策略
- `JwtAuthenticationTokenFilter`：请求 token 解析
- `GlobalExceptionHandler`：统一异常出参
- `DataScopeAspect`：后台数据权限拼接
- `RepeatSubmitInterceptor`：重复提交控制

说明：

- 后台接口默认需要认证和权限点控制
- `/api/**/**` 在安全配置中被放行，但很多 APP 接口仍通过 token 获取 `SecurityUtils.getUserId()`，即“安全配置允许匿名，不代表业务真实匿名”

### 5.3 `ruoyi-system`

职责：

- 承载全部核心业务模型和业务流程
- 维护实体、服务、Mapper、XML、定时任务、业务工具

当前规模：

- 业务实体：`113`
- Service 接口：`112`
- Mapper 接口：`117`
- 任务类：`26`
- `@Scheduled` 调度点：`37`

该模块是整个项目的核心。

### 5.5 `ruoyi-quartz`

## 8. 数据层与迁移分析

### 8.1 数据访问方式

项目使用 MyBatis XML，查询逻辑大多位于：

- `ruoyi-system/src/main/resources/mapper/system`

特征：

- 动态 SQL 较多
- 查询条件大量依赖 `BaseEntity.params`
- 逻辑删除普遍存在
- 数据权限通过 `${params.dataScope}` 动态拼接

### 8.2 数据库迁移方式

Flyway 脚本目录：

- `ruoyi-admin/src/main/resources/db/migration`

当前 migration 文件数量：

- `195`

说明：

- 该项目数据库已经历多轮迭代
- 当前数据库结构并不是“初始化 SQL 一次性导入”那么简单，而是持续演进出来的


## 9. 请求链路与权限特征

### 9.1 后台链路

典型链路：

- 前端后台登录 `/login`
- JWT + Redis 保存后台登录态
- 后台接口通过 `@PreAuthorize` 做权限点校验
- 列表查询可叠加 `@DataScope`

### 9.2 APP 链路

典型链路：

- `/api/**` 路径暴露 APP 功能
- 登录、注册、验证码等接口可匿名访问
- 很多业务接口虽然在安全配置层放行，但依旧通过 token 获取当前用户

结论：

- APP 权限模型是“路径层面偏宽松，业务层面再校验登录态”

### 9.3 审计与防重

当前项目对关键接口已广泛使用：

- `@Log`
- `@RepeatSubmit`

说明：

- 系统对操作审计和重复提交问题有明确防护意识
- 在资金、订单、审核类接口中尤为常见

综合模块和功能分布，可以把当前后端归纳为一个“多品类金融交易与运营平台”，其主要组成包括：

1. 用户中心
2. 钱包资金中心
3. 多产品交易中心
4. 理财/贷款/质押中心
5. 内容运营中心
6. 国际化与站点配置中心
7. 外部支付与通知接入中心
8. 定时任务驱动的自动处理中心
9. 若依后台基础设施中心


## 11. 项目特点与风险提示

### 11.1 特点

- 若依底座保留较完整，但业务层已经高度定制
- 控制器数量多，业务面广
- 金融属性明显，资金与订单链路复杂
- 国际化能力明显，不是单语言站点
- 自动任务很多，部分业务强依赖调度推进

### 11.2 风险提示

- `/api/**` 虽然被放行，但很多接口仍隐式依赖 token，不熟悉的人容易误判权限模型
- 默认时区为 `America/Toronto`，时间类问题很容易排查偏差
- `BaseEntity.params` 被广泛用作隐式查询参数，改动 SQL 时要格外注意
- 数据权限通过动态 SQL 注入实现，后台列表新增查询很容易漏权限
- 当前业务复杂度很高，但测试代码非常少，回归风险主要靠人工验证与编译检查


## 12. 后续接手建议

如果后续要继续深入本项目，建议按以下顺序建立认知：

1. 先熟悉 `ruoyi-admin` 控制器分层和接口入口
2. 再熟悉 `ruoyi-system` 中与“用户、资金、订单、产品”相关的 ServiceImpl
3. 再看 `task` 下的自动任务，理解订单和资产如何被异步推进
4. 再看支付、短信、邮件、Telegram、Udun 等外部接入工具
5. 最后再回头梳理 SQL、数据权限和缓存细节

如果是排查某条业务链，推荐从对应 Controller 开始，顺着：

`Controller -> ServiceImpl -> Mapper/XML -> 定时任务 -> 缓存/三方调用`

逐层追踪。
